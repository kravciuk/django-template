# Функциональные пробелы

## Главное: нет уведомлений об истечении гарантии/срока договора

Это, на мой взгляд, самое важное расхождение между тем, что заявлено как цель проекта ("контроль сроков
гарантии"), и тем, что реально реализовано. Поля `expires_at`/`remind_at` есть на уровне модели
(`apps.common.models.ExpiryModel`, наследуется `Note` и `Attachment`), в документах (`apps.documents`) их можно
задавать и фильтровать по ним, есть даже пассивный виджет "скоро истекающие документы" на главной странице — но
**ничто никогда не уведомляет владельца проактивно**: нет ни задачи в Celery Beat, ни email, ни push/in-app
уведомления, которые бы срабатывали от приближения `expires_at`/`remind_at`.

При этом в проекте уже есть полностью готовая инфраструктура для того, чтобы это сделать быстро:
`apps.notifications` (модель `Notification`, сервис `notify()`, доставка через WebSocket + REST API) и
Celery Beat (`core/celery.py`) уже работают и используются для похожих периодических задач (`cleanup_stale_drafts`,
`cleanup_old_notifications`). Предлагаемая реализация — новая периодическая задача (например,
`apps.documents.tasks.check_expiring_documents`, ежедневно), которая находит документы с
`remind_at <= now()` (или `expires_at` в пределах настраиваемого окна) и создаёт `Notification` через
`services.notify()` для владельца документа, дальше не требуя вообще ничего нового — уведомление придёт и в
колокольчик в шапке, и в REST API "непрочитанные". Стоит также предусмотреть флаг "уведомление по этому документу
уже отправлено", чтобы не спамить каждый день, пока документ просрочен.

## `Visibility.SHARED` не работает (см. `docs/apps/sharing.md`)

Если публичные ссылки на конкретную заметку/документ вообще нужны как фича (не только `PUBLIC`/`UNLISTED`) — это
отдельная задача на доделку вьюхи. Если не нужны — стоит явно убрать `SHARED` из доступных вариантов в
пользовательских формах, чтобы не создавалось ложное впечатление, что оно работает.

## Тестовое несоответствие в форме заметки (`NoteKind.NODE`)

Один упавший тест (`test_note_form_kind_field_only_offers_note_and_album`) указывает на нерешённый вопрос:
должен ли пользователь вообще видеть "Узел" как выбираемый тип заметки в обычной форме создания, или это
исключительно служебный/скрытый тип, создаваемый только автоматически. Стоит принять явное решение и либо
поправить тест, либо убрать `NODE` из выбора формы.

## "Виджет погоды" на главной странице заметок

Показывает прогноз погоды для Вильнюса всем посетителям без исключения — судя по названию соседней колонки в
шаблоне (`col-reserved`), это, похоже, оставленная заглушка/демо, а не завершённая функция. Предлагаю решить: либо
убрать его совсем, либо действительно привязать к геолокации/настройке пользователя, раз уж в проекте есть вся
инфраструктура GeoIP (`GEOIP_PATH`, ежедневное обновление базы) — сейчас она, кстати, тоже нигде фактически не
используется на уровне запроса (нет middleware, которое определяло бы геолокацию посетителя).

## `purge_trash` не запускается автоматически

Команда `python manage.py purge_trash` (окончательное удаление всего, что старше `TRASH_RETENTION_DAYS`) есть и
работает, но не привязана ни к Celery Beat, ни к cron — то есть корзина никогда не очищается сама. Рекомендую
добавить её в `beat_schedule` (`core/celery.py`) рядом с уже существующими ежедневными задачами.

## Логирование запросов (client_ip, статус, длительность) подготовлено, но не подключено

В `core/logging.py` уже заложены поля `client_ip`/`real_ip`/`cf_ip_country`/`cf_ray`/`method`/`path`/
`status_code`/`duration_ms` и фильтр, исключающий `/health/`/`/metrics/` из логов — но ни то, ни другое не
работает, потому что нет ни одного middleware, которое передавало бы эти данные через `extra=`. Похоже на
подготовленную, но не реализованную функциональность (в `.env.example` даже заранее заданы имена заголовков
Cloudflare). Если нужен полноценный access-лог с этими полями — недостающая часть — одно небольшое middleware.
