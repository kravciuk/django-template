# Безопасность: приоритетные меры

Список отсортирован по тому, что я бы делал в первую очередь, если бы продолжал разработку. Полное техническое
описание каждого пункта — в `docs/security-considerations.md` (на английском, там же ссылки на конкретные
строки кода).

## Приоритет 1 — сделать до того, как появится второй пользователь

1. **Ограничить загрузку вложений по содержимому файла, а не только по расширению.** Сейчас
   `ATTACHMENTS_ALLOWED_EXTENSIONS` по умолчанию пуст (= без ограничений вообще), а даже при заданном списке
   проверяется только расширение имени файла — не реальное содержимое. Рекомендую задать белый список расширений
   в `.env` уже сейчас (в `.env.example` он уже подготовлен, но не активирован в реальном `.env`) и добавить
   проверку "магических байт" (например, через `python-magic`) хотя бы для PDF/Office-форматов, которые
   действительно ожидаются в этом проекте (договоры, чеки, гарантийные талоны).

2. **Закрыть SSRF в получении favicon (`apps.links`)** до того, как ссылками смогут пользоваться менее доверенные
   пользователи — сейчас сервер по любой ссылке пользователя обращается к `<хост из ссылки>/favicon.ico` без
   проверки на приватные/локальные адреса.

3. **Доделать `apps.sharing` целиком, а не только модель.** Сейчас в базе можно создать `ShareLink`, но по нему
   ничего нельзя открыть — ни хорошо, ни плохо, работа просто не завершена. Если фича "поделиться по ссылке"
   вообще нужна — стоит доделать её сразу правильно, закрыв заодно два найденных дефекта (привязка ссылки к
   объекту, проверка на корзину) в процессе реализации, а не после.

## Приоритет 2 — стоит сделать, но не блокирует

4. **Логирование WebSocket-запросов в nginx.** Если когда-нибудь появится клиент, использующий JWT через
   `?token=` в WebSocket URL (сейчас браузерный клиент им не пользуется, аутентификация идёт через cookie сессии)
   — токен будет попадать в access-логи nginx в открытом виде. Стоит добавить `access_log off` (или маскирующий
   `log_format`) для `/ws/` заранее, до появления такого клиента.

5. **Ограничить, кому staff-пользователь может отправить уведомление через админку** (`apps.notifications`,
   "Send notification") — сейчас получателем может быть любой пользователь системы без ограничений. Вероятно,
   это осознанно для доверенного административного инструмента, но стоит явно зафиксировать это решение.

## Не срочно, но зафиксировано для истории

6. Гонка при проверке лимита использований `ShareLink` (`max_uses`) — некритично при низкой нагрузке, но стоит
   сделать атомарным при реализации п.3 выше.
7. Рассинхронизация между `COMMENTS_MAX_DEPTH` (настройка) и жёстко зашитым ограничением в БД
   (`CheckConstraint`, максимум 5) — если когда-нибудь захотите увеличить глубину комментариев, не забудьте про
   миграцию для этого constraint'а.
