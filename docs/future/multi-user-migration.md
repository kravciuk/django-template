# Переход на многопользовательский режим

Проект изначально спроектирован под одного владельца, но архитектура уже во многом к этому готова — большинство
моделей и view используют `owner`/`request.user` для фильтрации, и явных "single-user shortcuts" (типа
`User.objects.first()`) я не нашёл ни в одном из проверенных приложений. Тем не менее есть несколько мест, которые
стоит пересмотреть **до** открытия проекта для нескольких пользователей.

## 1. `apps.sharing` нужно либо достроить, либо явно отключить `Visibility.SHARED`

Сейчас `ShareLink` можно создать через админку, но открыть по ссылке нельзя — `apps/sharing/urls.py` не содержит
ни одного реального маршрута (единственная строка закомментирована), и `views.py` в приложении вообще нет
(подробности — `docs/apps/sharing.md`, `docs/security-considerations.md`, SEC-1..SEC-3). Пока это не доделано,
это не баг многопользовательского режима как такового, а незаконченная фича. Но если в многопользовательской
версии предполагается "поделиться заметкой с конкретным человеком по ссылке" — это тот самый механизм, и его
стоит доделать одним из первых, заодно закрыв два уже найденных дефекта:
- проверку, что `ShareLink` действительно относится к запрашиваемому объекту (сейчас это не проверяется вовсе);
- проверку, что объект не находится в корзине (soft-delete).

## 2. Глобальный автокомплит тегов

`apps.content.views.tag_suggest` ищет теги **по всем пользователям сразу** — это осознанный выбор для
single-user режима (в коде есть соответствующий комментарий), но при нескольких пользователях один пользователь
сможет через автокомплит увидеть, какими тегами пользуются другие. Нужно решить: либо ограничить выборку
`owner=request.user`, либо явно оставить теги общими (например, если предполагается общий словарь категорий) —
но тогда стоит убрать компонент из "приватного" контекста заметок.

## 3. Комментарии — общедоступны для любого, кто видит объект

`apps.comments` разрешает комментировать любой объект с visibility=PUBLIC любому аутентифицированному
пользователю, а не только владельцу. Это выглядит как осознанное решение в духе блога, но стоит явно
зафиксировать, что это ожидаемое поведение для будущей многопользовательской версии — иначе это можно принять за
недоработку прав доступа.

## 4. `apps.links.Link` не имеет собственного `owner`

Владение определяется только через `group.owner` (а `Link.author` — это "кто добавил ссылку", что в
single-user режиме совпадает с владельцем, но не обязано совпадать в будущем — например, если несколько
пользователей когда-нибудь получат доступ к одной группе ссылок). Если такой сценарий совместного доступа к
группам ссылок не планируется — ничего делать не нужно, просто держите это в уме при следующих правках `apps.links`.

## 5. SSRF при получении favicon (`apps.links`)

Один пользователь может спровоцировать серверный запрос на любой хост (включая внутреннюю сеть/облачные
метаданные) через поле URL ссылки — подробности в `docs/security-considerations.md`, SEC-5. Для одного
доверенного владельца это не критично, но при нескольких пользователях с разным уровнем доверия это уже
полноценный вектор атаки на инфраструктуру. Рекомендую закрыть до открытия регистрации новым пользователям:
запрет на приватные/локальные адреса после DNS-резолвинга, ограничение схемы `http`/`https`, отключение
автоматических редиректов (или их повторная проверка).

## 6. Права на вложения при смене видимости документа

Новое вложение получает `visibility` родительского документа только в момент создания — если видимость документа
меняется позже, уже прикреплённые файлы её не наследуют. В single-user режиме это не проблема (один владелец), но
при разграничении доступа между пользователями стоит явно решить: либо каскадно синхронизировать видимость
вложений с родителем, либо сделать это осознанным ограничением с явным UI-предупреждением.

## 7. Регистрация пользователей

Сейчас нет ни одного способа завести нового пользователя, кроме `manage.py createsuperuser` / админки —
`apps.users` не содержит `views.py`, строка `RegisterView` в `urls.py` закомментирована. Это первое, что
потребуется реализовать технически для перехода к многопользовательскому режиму (собственно "открыть двери").
При этом стоит сразу продумать: `User.json_data` (сейчас произвольный JSON без схемы) и `registration_ip`
(сейчас нигде не заполняется) — оба поля, скорее всего, должны получить реальное наполнение в рамках этой же
работы.
